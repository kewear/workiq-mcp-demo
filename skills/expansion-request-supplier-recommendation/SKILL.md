Processes supplier recommendation, calls Human_In_the_loop_approval, and delegates approved awards to finalize-vendor-award. ---  # Expansion Request Supplier Recommendation  ## Purpose  Process an Expansion Request business event when the request is ready for supplier recommendation. This skill finds the request, obtains or reads the supplier recommendation, calls the workflow tool `Human_In_the_loop_approval`, waits for the returned decision, and then delegates approved awards to the `finalize-vendor-award` process skill.  ## Event handled  `ExpansionRequest.ReadyForSupplierRecommendation`  ## Inputs  The event payload must include:  - `eventType` - `requestNumber` - `status`  The event payload must not include Dataverse environment details. The skill owns the configured `D365AITour` environment binding.  ## Eligibility checks  Proceed only when all of the following are true:  - `eventType` equals `ExpansionRequest.ReadyForSupplierRecommendation` - `status` equals `Ready for supplier recommendation` - `requestNumber` is present  If any eligibility check fails, stop and return a concise explanation of why no action was taken.  ## Required execution order  1. Find the Expansion Request by `requestNumber` in the configured `D365AITour` environment. 2. Confirm the request exists and is ready for supplier recommendation. 3. Discover the supplier recommendation business skill by name. 4. Invoke the supplier recommendation business skill only if an executable action/tool is exposed. 5. If the supplier recommendation skill is metadata-only, read grounded recommendation data from the Expansion Request and related records instead of inventing values. 6. Call `Human_In_the_loop_approval` with `Approve` and `Reject` options. 7. Wait for the approval decision returned by `Human_In_the_loop_approval`. 8. If the decision is `Approve`, call the GitHub process skill `finalize-vendor-award` and pass the request number, approval decision, and available recommendation context. 9. If the decision is `Reject`, do not finalize. Report that the recommendation was rejected.  The process is incomplete if `Human_In_the_loop_approval` was not called.  ## Work IQ and Business Applications rules  Use Work IQ MCP for Business Applications discovery and actions.  Business skills are discoverable by name. Do not assume they are Dataverse Custom APIs. Do not invent `/customapis/...` paths.  Supplier recommendation business skill names to search for:  - `Recommend Supplier and Initiate Vendor Award` - `cr2d6_skill_recommend_supplier_and_initiate_vendor_award`  To run a business skill, use only an executable action/tool path that is actually exposed in the current run. Valid executable surfaces include an attached workflow tool, a returned Business Applications action path, or another concrete action path returned by Work IQ discovery with an `action` operation.  If discovery returns only skill metadata with `fetch`, `update`, or `delete`, do not treat that as execution.  If the supplier recommendation business skill is not executable in the current run, but grounded recommendation data already exists, continue to approval using that grounded data.  ## Approval tool rule

### Fresh approval requirement

A fresh approval is required for every new business event processed by this skill. Do not reuse, infer, or rely on a prior recorded approval decision from an earlier run, Teams card, Dataverse row, transcript, or memory. Historical approval data may be mentioned as context only, but it does not satisfy this run's approval gate.

Call `Human_In_the_loop_approval` after grounded recommendation data is available, even if a previous approval exists for the same request number. The current run is incomplete until this tool is called and returns a decision.  For human approval, call the attached workflow tool named `Human_In_the_loop_approval`.  Do not construct Teams cards manually. Do not use Work IQ Teams messages for the approval gate.  The approval payload should include:  - Request number - Recommended supplier, or `Pending` if not available yet - Budgeted amount, if available - Award amount, if available - Reason for recommendation, or `Pending` - Vendor Award identifier, if available - Options: `Approve`, `Reject`  ## Decision handling  If `Human_In_the_loop_approval` returns `Approve`:  - Call the GitHub process skill `finalize-vendor-award`. - Pass `requestNumber`, `approvalDecision`, and any available recommendation context. - Do not ask the user whether to finalize.  If `Human_In_the_loop_approval` returns `Reject`:  - Do not call finalization. - Report that the recommendation was rejected. - If an exposed rejection/status update action exists, use it. Otherwise, report rejection as the final workflow outcome.  If the approval decision is missing, ambiguous, or failed:  - Do not finalize. - Report the approval failure clearly.  ## Safety rules  - Do not finalize before `Human_In_the_loop_approval` returns `Approve` for the current run.\n- Do not reuse a prior approval decision as the approval result for the current run. - Do not create duplicate Vendor Awards if one already exists for the request. - Do not create, edit, update, publish, or overwrite business skill definitions. - Do not claim completion unless the approval gate and any required downstream action succeeded. - If a tool call fails, report the failure clearly and stop.  ## Success response  Return a short summary with:  - Request number - Recommended supplier - Approval decision - Finalization outcome - Current status
